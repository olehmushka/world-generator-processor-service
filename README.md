# world-generator-processor-service

An HTTP backend service that wraps [world-generator-engine](https://github.com/olehmushka/world-generator-engine) —
a procedural worldbuilding generator that produces languages, genders, gender acceptances,
cultures and traditions for fictional worlds — and persists the generated data so it can be
served, queried and extended over an API.

It is the "capstone" service of a small personal Go ecosystem:

- **[world-generator-engine](https://github.com/olehmushka/world-generator-engine)** does the
  actual procedural generation (languages, genders, cultures, traditions, ethoses, origins, ...).
  It has no notion of persistence or HTTP — it just generates data in memory.
- **world-generator-processor-service** (this repo) wraps that engine, syncs its generated
  ("native") data into durable storage (Postgres, with MongoDB and Redis also available as
  storage/cache backends), and exposes it as a documented HTTP API.
- **[postgres-golang](https://github.com/olehmushka/postgres-golang)** and
  **[golang-toolkit](https://github.com/olehmushka/golang-toolkit)** are shared helper libraries
  (Postgres client/transaction helpers, error wrapping, context helpers, HTTP server helpers, etc.)
  used across the author's Go services, including this one.

> Status: this is a personal/portfolio project. It's functional but intentionally scoped — see
> "Known limitations" below for what's not (yet) built out.

## Architecture

The service follows a layered architecture:

```
cli/                    CLI entry points (cobra-less, simple command dispatch)
config/                 Environment/config loading (godotenv + configor)
core/
  engine/               Adapter over world-generator-engine (the generation library)
  http_server/           go-chi based HTTP server, router, middleware
  storage/
    postgres/            Postgres reader/writer clients (via postgres-golang)
    mongo/                MongoDB client wrapper
    redis/                Redis store + pub/sub publisher/consumer
  tools/                 Cross-cutting helpers: trace IDs, HTTP error responses
  zerodowntime/          Graceful start/stop handling for the fx app
internal/<domain>/       One package per domain: cultures, genders, languages, traditions, users
  entities/               Domain models persisted/returned by the service
  services/               Business logic (e.g. "sync" services that pull native data
                           from the engine and persist it if it doesn't exist yet)
  adapters/
    engine/                Translates world-generator-engine types into this service's entities
    storage/                Translates entities into/out of the storage layer
  repos/
    commands/                 Write queries (SQL)
    queries/                   Read queries (SQL)
    tx/                        Transaction helpers
handlers/http/           HTTP handlers (health check, info, and Swagger-documented endpoints)
migrations/               golang-migrate SQL migrations (schema, genders, gender acceptance,
                           traditions, cultures)
docs/                     Swagger docs generated by swaggo (`swag init`)
```

Dependency wiring is done with [`go.uber.org/fx`](https://github.com/uber-go/fx): each layer
exposes an `fx.Options`/`fx.Module`, and the CLI commands compose the modules they need (e.g. the
HTTP server command wires in the full stack, `migrate_up`/`migrate_down` only need Postgres
config, `sync_data` wires in the sync services for each domain).

Each domain under `internal/` follows the same shape: an **engine adapter** loads "native" data
generated by world-generator-engine and maps it onto the domain's own entities, a **storage
adapter** knows how to read/write those entities via the domain's repos, and a **sync service**
ties the two together — for each item produced by the engine, check if it already exists in
storage (by slug) and create it if not, all within a transaction.

### API

The HTTP API is documented with [Swagger](https://swagger.io/) via
[swaggo/swag](https://github.com/swaggo/swag) annotations on the handlers in `handlers/http/`.
Once the server is running, the interactive docs are served at `/api/docs/index.html` (base path
configurable via `HTTP_SERVER_BASE_PATH`). At the moment the exposed endpoints are:

- `GET /api/info` — basic service info
- `GET /api/health-check` — health check

Regenerate the docs after changing handler annotations with:

```sh
make swag_init
```

## Running locally

### Prerequisites

- Go 1.18+
- Docker (for Postgres and MongoDB)
- A Redis instance reachable at `REDIS_URL` — the storage layer wires up a Redis client
  unconditionally, but `docker-compose.yml` currently only defines Postgres and MongoDB, so run
  one yourself if you need it, e.g. `docker run -p 6379:6379 redis`.

### 1. Configure environment

Copy the sample env file and adjust as needed:

```sh
cp .env.sample .env
```

### 2. Start dependencies

```sh
docker-compose up -d
```

This starts:

- `pg-mongo` — MongoDB on `localhost:27017`
- `pg-postgres` — Postgres on `localhost:5432` (with `pg-init-scripts/` creating the
  `worlder_db` database/user on first boot)

### 3. Run database migrations

```sh
make migrate_up
```

### 4. Sync generated data into storage

Pulls native data (languages, genders, gender acceptances, ...) out of
world-generator-engine and persists anything not already stored:

```sh
make sync_data
```

### 5. Run the HTTP server

```sh
make run_http_server
```

The server listens on `HTTP_SERVER_ADDRESS` (default `:8080`) with base path
`HTTP_SERVER_BASE_PATH` (default `api`).

## CLI commands

All commands are run via `go run main.go <command>` (or the equivalent `make` targets):

| Command            | Make target          | Description                                                                 |
|---------------------|----------------------|-------------------------------------------------------------------------------|
| `http_server_run`   | `make run_http_server` | Starts the HTTP API server.                                                 |
| `migrate_up`        | `make migrate_up`      | Applies all pending Postgres migrations from `migrations/`.                 |
| `migrate_down`      | `make migrate_down`    | Rolls back Postgres migrations.                                             |
| `sync_data`         | `make sync_data`       | Loads native data from world-generator-engine and persists new records.     |

## Development

```sh
make install          # go mod download
make test             # go test ./...
make test_coverage    # go test -cover ./...
make fmt              # go fmt ./...
make lint             # golangci-lint run
make tidy             # go mod tidy
```

Tests that exercise pure logic (mapping/transformation functions, HTTP handlers, storage-agnostic
helpers) run without any external services. Tests that require a live Postgres/MongoDB/Redis
connection are not part of the current suite — see "Known limitations" below.

## Known limitations

This is a personal project, not a production system, and some things are deliberately not (yet)
built out:

- No integration tests against real Postgres/MongoDB/Redis instances (only unit tests over pure
  logic and HTTP handlers).
- Only two domains (`genders`, `languages`) are currently wired into `sync_data` and the fx
  module graph in `cli/modules.go`; `cultures` and `traditions` have entities/services but aren't
  fully wired up yet, and `users` only has entities so far.
- The HTTP API currently only exposes health/info endpoints; the generated domain data
  (languages, genders, cultures, traditions) is persisted but not yet exposed via REST endpoints.
- `docker-compose.yml` only provisions Postgres and MongoDB, not Redis or the service itself.
